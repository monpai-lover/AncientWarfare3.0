# AW3 空世界逐年卡死性能问题调查报告

日期：2026-08-11

状态：调查暂停，保留证据，不继续扩大排查

优先级：性能优先

## 1. 问题定义

用户稳定观察到：即使新地图中几乎没有单位、没有战争、没有 RTS 军队，游戏在运行数年后仍会逐步掉帧，通常从第三年左右开始明显，最终可能长时间卡顿或接近卡死。

这个问题的关键特征不是单次年度更新峰值，而是持续运行后基础帧耗逐渐上升，并伴随周期性严重停顿。

## 2. 当前结论

目前能够确认的结论如下：

1. 这轮代表性复现不是 RTS、战争或军队寻路导致的。
2. 这轮代表性复现也不是异步任务积压或 worker 数量不足导致的。
3. 没有发现死亡 Actor、销毁队列、学校队列或王国修复队列持续堆积。
4. 游戏运行期间托管堆持续快速增长，并在完整 GC 时出现肉眼可见的停顿。
5. 已测量的 Actor 模拟、建筑和 AW3 权力/政策任务只能解释 `MapBox.Update` 的一小部分耗时，仍有约 `7-8ms` 每帧没有被现有分项覆盖。
6. 当前最强候选是每帧表现与可见对象处理链产生了高频临时分配，但这仍是候选，不是已经证明的最终根因。

因此，当前问题更符合“未覆盖的每帧路径持续制造临时对象，托管堆快速膨胀并触发完整 GC”的模型，而不是“后台线程把主线程堵住”或“寻路请求越积越多”的模型。

## 3. 代表性复现数据

一次干净复现使用了原版寻路和 native 调度模式，关键数据如下：

| 指标 | 早期 | 后期/峰值 | 说明 |
| --- | ---: | ---: | --- |
| FPS | 约 56 | 约 33 | 随运行时间下降 |
| `MapBox.Update` | 约 3.6ms | 约 9.5ms | 基础帧耗明显增长 |
| 存活 Actor | 约 82 | 约 270 | 数量增长，但不足以解释全部帧耗 |
| Actor 模拟 | 约 0.8ms | 约 0.8ms 量级 | 不是主要缺口 |
| 建筑更新 | 约 0.5ms | 约 0.5ms 量级 | 不是主要缺口 |
| 已测 AW3 权力任务 | 约 0.2ms | 约 0.2ms 量级 | 不是主要缺口 |
| 未解释的 MapBox 时间 | - | 约 7-8ms/帧 | 需要进一步分段定位 |
| 托管堆 | 约 715MB | 约 1176MB | 随后发生完整 GC |
| 进程 CPU | 约 1.0-1.5 个逻辑核 | 基本相同 | 不是 32 线程算力耗尽 |

完整 GC 与用户看到的严重停顿时间吻合。当前证据支持“高分配率”而不是“长期保留大量已经死亡的对象”。

## 4. 已排除或暂不支持的方向

### 4.1 寻路

代表性复现中：

- `path requests=0`
- 使用原版寻路仍然复现
- 没有军队和战争

所以这次空世界逐年卡死不能归因于 Cultiway 寻路移植、RTS 路径请求或寻路 worker 数量。

这不代表寻路代码不存在其他独立问题，只代表它不是本轮复现的主因。

### 4.2 RTS 与战争

代表性复现中：

- `army_count=0`
- 没有战争
- 没有 RTS 指令、补员或集结活动

因此战争期间的卡顿可以另行分析，但不能解释“什么都不放，运行几年也会卡死”。

### 4.3 异步队列与 worker 数量

代表性复现中：

- `async_queued=0`
- `async_active=0`
- 关闭异步选项后，卡顿仍会以其他 profiler 分类出现
- CPU 只使用约 1.0-1.5 个逻辑核

Profiler 中 `async_compute` 或 `runtime_pathfinding` 哪个分类变大，会受到开关和调用包装层归属影响，不能单凭分类名称认定后台任务是根因。现有数据没有显示异步积压。

增加 worker 可能改变调度表现，但不会修复本轮已经确认的托管堆快速增长。

### 4.4 死亡 Actor 或维护队列泄漏

诊断结果显示：

- `total_actor_objects` 与存活人口基本一致
- `dying_actor_objects=0`
- `actor_destroy_queue=0`
- 学校死亡/后代待处理队列为 0
- deferred runtime work 为 0
- kingdom repair queue 为 0

所以当前没有证据表明死 Actor、待销毁 Actor 或这些维护队列在持续保留整个对象图。

### 4.5 年度任务

年度更新确实可能产生独立峰值，之前也发现过文化命名迁移重复请求、外交年度空引用等问题。但本轮持续掉帧发生在非年度帧，年度任务不能解释全部现象。

## 5. 当前最强候选链

现有分项无法解释 `MapBox.Update` 后期增加的约 `7-8ms`，剩余未充分覆盖的高频路径主要是：

1. `MapBox.calculateVisibleObjects`
2. `ActorManager.calculateVisibleActors`
3. `Actor.updatePos` / `Actor.updateRotation`
4. `Actor.calculateMainSprite`
5. `QuantumSpriteManager.update`
6. `MapBox.renderStuff`

这些路径具备两个符合现象的特征：

- 每个渲染帧都会执行，能够造成非年度持续卡顿。
- 会随可见 Actor 数量和表现对象数量增长，可能产生大量短命对象或集合扩容。

但截至暂停调查时，还没有获得这些阶段各自的耗时和分配量，所以不能把“表现链”写成最终根因。下一轮若恢复调查，应先做低开销的分段归因，再针对被证明的阶段写修复，而不是直接改动画或调度器。

## 6. 1.2.1 对比实验为什么无效

之前进行的 1.2.1 A/B 不能作为版本结论，原因是 `Mods` 目录内同时存在两个相同 GUID 的 AW3 目录：

- `AncientWarfare3.0`
- `.AncientWarfare3-current-perf-ab`

NML 日志明确记录：

```text
Repeat Mod with ANCIENTWARFARE3, Only load one of them
```

当时编译程序集仍包含 1.2.2 才有的类型，说明 NML 选择或复用了错误源码。因此不能据此判断 1.2.1 也存在同一回归，也不能据此确定是哪次提交引入。

环境现已恢复为：

- `Mods` 下只保留 `D:\SteamLibrary\steamapps\common\worldbox\Mods\AncientWarfare3.0`
- 旧版目录移到 `D:\SteamLibrary\steamapps\common\worldbox\.AncientWarfare3.0-backup-20260810-180429`
- 大步长配置已恢复

后续若重新做 A/B，必须使用隔离 worktree 或唯一部署目录，并验证实际加载程序集包含的版本类型。

## 7. 已保留的诊断能力

当前源码保留了已经产生有效证据、且关闭性能诊断时不会执行世界扫描的计数：

- 真实帧间隔与平均 FPS
- `MapBox.Update` 平均耗时和帧外时间
- 进程 CPU、工作集、私有内存、线程和句柄
- 托管堆与各代 GC 次数
- 存活、死亡、待销毁 Actor 数量
- 学校、延迟工作和王国修复队列长度
- 异步提交耗时与队列状态

本轮刚开始编写、尚未通过测试的 MapBox 分阶段 Harmony 诊断补丁已经从工作区清除，避免把半成品补丁带入正式分支。

## 9. 若恢复调查，正确的下一步

1. 在性能诊断开启时，按 `updateSimulation`、可见对象、Actor 表现、渲染分发和 QuantumSprite 五段采集耗时与线程分配量。
2. 保证诊断关闭时不增加每帧反射、集合分配或 Harmony 热路径开销。
3. 在唯一部署目录下复现到约 15000 帧，比较各阶段耗时、分配、托管堆和完整 GC。
4. 只对已证明的主导阶段写失败测试和根因修复。
5. 修复后再做真正隔离的 1.2.1/当前 master A/B，确认回归归属。
