# 姓氏编辑与藩王身份约束设计

## 目标

修复族谱窗口的改氏目标与更新范围错误，增加从指定人物开始改姓的能力，并保证在任藩王不会保留或重新获得奴隶身份。

## 已确认语义

- 改氏在氏族大树中执行，作用于当前 `shi_id` 的完整氏支，包括氏支始祖本人、活人和历史档案人物。
- 改姓在家庭树中执行，作用于当前居中人物本人以及其全部父系后代。
- 父系链上的男性成员及其亲生女儿都采用新姓，但遍历不再沿女儿的子女继续，女儿的子女仍按其父系继承。
- 改姓不影响目标人物的兄弟、叔伯、父系祖先或从其他男性祖先分出的旁支。
- 藩王受封时立即脱离奴隶身份；担任藩王期间，任何奴役入口都必须拒绝该人物。
- 藩王失去爵位后不恢复旧奴隶身份，但以后可以按正常规则重新被奴役。

## 根因与修复边界

现有改氏 UI 使用 `_backShiId` 提交命令。该字段兼具“家庭树返回目标”和“当前大树氏支”两种含义，容易把当前目标回退到姬发所在根氏支。命令端又通过 `RulerOwnsShi` 要求当前国王属于目标氏支，因此普通诸侯氏支无法执行改氏。

修复后，大树改氏从当前读取快照的明确 `ShiId` 建立请求，不再使用返回导航状态推导目标。单机可编辑当前查看的任意氏支；联机仍通过主机权威命令执行和同步，但授权依据为玩家是否有权操作当前国家，而不是国王是否属于该氏支。

现有氏支收集依赖 `ActorArchive.SHI_ID` 和活人 `SHI_ID`。实现必须显式包含氏支表记录的始祖 Actor，并对活人/档案 ID 去重，避免只改后代、不改始祖。

## 改姓数据流

家庭树侧边新增“改姓”入口。目标 Actor ID 取当前家庭树中心 `_centerActorId`。命令到达权威端后：

1. 校验目标存在于活人数据或人物档案，并规范化新姓。
2. 通过归档父子关系沿 `father_id` 有界遍历，收集目标本人及父系后代；同时合并尚未完整归档的活人父子关系。
3. 使用 visited 集合防止损坏存档中的循环关系造成无限递归。
4. 对每个目标更新 `FAMILY_NAME` 和 `CHINESE_FAMILY_NAME`。
5. 重建活人显示名、刷新贴图并更新人物档案的 `FAMILY_NAME` 与 `DISPLAY_NAME`。
6. 推进历史内容修订号并刷新族谱窗口缓存。

既有出生继承仍读取父亲的 `FAMILY_NAME`，因此修改后出生的父系子孙会自然继承新姓，不需要额外的长期覆盖规则。

## 改氏数据流

改氏继续更新当前氏支的 `ShiBranch.CLAN_NAME`。收集目标时包含氏支始祖、所有相同 `shi_id` 的档案人物以及活人。每个目标同步更新 `CLAN_NAME`、显示名和档案；原版 Clan 的展示名称在有对应活人领袖时同步刷新。

## 藩王非奴隶不变量

`FeudatoryService` 在受封事务成功并发布运行时快照后调用统一身份修复：

- 从奴隶人口索引和临时奴隶军索引移除；
- 清除奴隶 trait、奴隶军标记、奴隶主/俘获来源和奴隶任务；
- 恢复贵族身份、藩王 trait、藩王职业与显示名；
- 更新人物档案和奴隶持久化状态。

`SlaveService.CanBeEnslaved` 增加 `FeudatoryService.IsActivePrince` 拒绝条件，覆盖俘虏、占领、出生继承等所有通过统一奴役入口的路径。读取存档重建藩王缓存后，批量检查在任藩王并执行同一身份修复，以修复旧档冲突。

## 联机与一致性

改姓和改氏都使用 AW3 权威命令路由。客户端只发送目标 ID 和规范化前文本；主机重新校验范围、执行数据库与运行时更新，再由现有同步机制传播结果。客户端不得直接修改族谱数据库。

## 测试

- 大树处于非姬发氏支时，命令使用当前快照 `ShiId`。
- 改氏包含氏支始祖本人，并更新活人与历史档案。
- 改姓包含目标本人、儿子、女儿和经男性成员延续的孙辈，不包含兄弟、父亲、女儿的子女或无父系关系人物。
- 损坏的循环父子数据不会无限遍历，活人和档案重复 ID 只更新一次。
- 显示名同时反映新姓或新氏，后续出生子女继承新姓。
- 受封会清除既有奴隶状态；存档重建会修复冲突状态。
- 在任藩王经普通、占领、重要人物俘虏路径均不能再次被奴役。
- 失去藩王身份后不会恢复旧奴隶状态，但可按正常规则再次被奴役。

## 非目标

- 不修改姓氏合流、分封立氏和历史人物初始姓氏规则。
- 不让改姓自动创建新的氏支或新的父子关系。
- 不修改族谱窗口的整体布局。
